## 2. Compiler and libraries

### Verdict

**Metrowerks CodeWarrior for PlayStation 2, with the MW linker, for the game, RenderWare, the RWA client, GTFS, the EA network stack and the MSL C++ runtime.** Confidence high. The prebuilt third-party archives (Sony SDK 2.8.0 libraries, Sony libc/libm, Logitech libraries with Speex, two unidentified Sony RPC clients) were built by a second compiler whose frame shape matches ee-gcc 2.9x; confidence medium, because no SDK or CodeWarrior binary exists on either machine to compare against. Not ee-gcc for the game, not SN ProDG.

### Evidence (verified unless marked)

1. `llvm-readelf-18 -p .comment` prints exactly `MW MIPS C Compiler (2.4.1.01)` and `PlayStation2`. No "GCC:", "GNU", "ProDG", "SN Systems", `sn_`, `_Z`, `__ct`, `__cxa`, `__gxx`, `_Unwind`, `.ctors` or `.eh_frame` string exists anywhere in the file. The MW linker drops input `.comment` sections, which is why zero GCC banners survive although Sony's archives were gcc-built.
2. Prologue census over the raw words: 6,021 functions adjust `sp` with `addiu`, none with `daddiu`. About 4,000 functions save their callee-saved registers with the 128-bit `sq` store and keep `ra` at about half the frame (the Metrowerks shape); about 780 save them with `sd` into 16-byte slots with `ra` at the top of the frame (the ee-gcc EABI64 shape). The two shapes never mix inside a library run: every claimed vendor range is 100% the second shape and every game and RenderWare range is 100% the first. (Correction to the reader's note: `daddiu` itself appears 1,411 times in the image and `daddu` 59,348 times in both dialects, so neither discriminates the compilers; only the prologue does.)
3. MSL runtime strings at `0x004B1500`-`0x004B16B0` (`std::exception`, `std::bad_exception`, and the `!A!!B!!` base-class chains) are the Metrowerks RTTI encoding; GCC stores mangled names. Referenced from `0x00100458`, `0x00100FE8`, `0x0010105C`, `0x00101FC8` (the exception runtime right after crt0) and from data words `0x004B1510`, `0x004B16A8`, `0x004DDAA0`, `0x004DDAB0`.
4. Static initialisers are linked after `.data` (`0x004D3E00`-`0x004DD7E0`) with a plain pointer table at `0x004DD820`-`0x004DDA98` (158 words, all targets inside that range) and a runner at `0x00100810`: the MW `__sinit` layout, not GCC `.ctors`.
5. The printf family is Sony's newlib-derived libc ("bug in vfprintf: bad base" at `0x004B3868` and "(null)", referenced from `0x00127C80`-`0x0012E858` according to the ELF reader; the verifier confirmed that run is wholly the second dialect), so CodeWarrior was used with Sony's libc, the standard configuration.
6. Upstream corroboration: the GPL matching project on this same ELF (siddharthakumar-98/Burnout3, knowledge only) names CodeWarrior PS2 3.0.1 build 119 (decomp.me `mwcps2-3.0.1b119-040914`) at `-O4 -str readonly -Cpp_exceptions off`. Reconciliation (guess): 3.0.1b119 is the CodeWarrior product build and 2.4.1.01 is the `mwccmips` component banner. The decomp.me build is dated 2004-09-14, a week after the NTSC-U release, so an exact match is not guaranteed.

What the Metrowerks dialect means for reading the code: switch jump tables live in `.rodata` (264 of them, 4,315 targets), callee-saved registers are saved 128-bit, `ra` sits mid-frame, no `daddiu` in prologues, and vector helpers and the PRNG are inlined. Heuristics tuned for ee-gcc prologues (m2c, Ghidra) will misjudge frames.

### The libkernl island (corrected)

The code at `0x004843D0`-`0x004854E8` is libkernl's kernel-patch material: three blobs that libkernl copies into kernel RAM (`0x80075000`, `0x80074000`, `0x80076000`) and installs as syscalls 0x5B/0x5A/0x83 handlers, with their tables and variables in between (verified from the installers at `0x00114600`-`0x001146FC`, `0x00114FF8`, `0x00115230`, `0x00115630` and run logs). Their "calls to kernel addresses `0x741E8`-`0x76460`" are self-references at the relocated addresses. The two words `0x00484890`/`0x00484894` are semaphore ids written by `0x00114ED0` (two `CreateSema` calls), not code; the recompiler's "function" at `0x00484890` was seeded from the export table at `0x0041BCF0` and is unreachable (nothing calls `unit_00E1`). Under the fork no blob ever executes: `handle_syscall` runs a custom handler only when `has_code()` is true, so syscall 0x5B is HLE'd to 0 (`kernel.cpp:689`) and libkernl then re-installs syscalls 0x55-0x59 with handler 0, which is currently benign. Worth a line in the fork's known-gaps list; not a translation hole.

## 3. Function population

Measured by the ELF reader with `eerecomp SLUS_210.50 --entries games/burnout3/entries.txt --out <scratch> --stats` (13.8 s) and an independent scan of the disassembly. The verifier re-derived the function-count range, the 2,407-candidate breakdown, the giants and the three false functions; the gap lists, data pockets, size and reachability figures are the reader's (reported):

- The recompiler: 861,427 instructions (3,364 KiB) in 6,113 functions, 67,234 entries, 0 rejected seeds, 225 units of 16 KiB. `entries.txt` holds one seed, `0x00469AB0`. The generated tree has 109,623 labels and is byte-identical to the fork's `generated/burnout3`.
- Independent counts: 7,145 distinct `jal` targets in the image (5,942 translated; the rest are data words decoding as `jal`); 158 constructor-table targets; 264 switch jump tables (4,315 targets); 89 vtable or callback tables (1,082 targets, 56 also called directly); 4,247 labels referenced by a data word.
- Function count: the defensible range is 6,101 (jal targets + ctors + entry) to about 7,030. The 2,407 extra pointer-referenced candidates are all already dispatch entries in the generated code; about 927 of them are real function starts (a stack-frame prologue within four instructions, or preceded by a function end). The rest are switch cases after a jump-table dispatch (273), blocks after an unconditional branch (527), fall-throughs (237) and other mid-function blocks; 540 use a callee-saved register before saving it. So the reader's upper figure of 8,508 was too high, and this is a counting matter, not a translation gap.
- Median function size 160 bytes, mean 429. Largest after the three giants: `0x002E90F0` (14,288 bytes), `0x003B2830`, `0x001C8870`, `0x002F0640`, `0x003DE1F0`, `0x00406E20`, `0x00223130`, `0x001108B0` (libkernl), `0x002D5918`.
- Reachability over 7,127 starts: 3,763 reached from the entry by direct calls alone, 3,926 with the constructor table, 6,482 with the vtable and callback tables, 645 only through single pointers or `jalr`.
- Translation coverage: 3,445,708 of 3,618,656 code-span bytes, 95.2%. ## 5. Crosswalk results

Method: the reB3 anchors (strings, tables, float constants, call-graph shape, struct-offset fingerprints) were searched in the ELF, the enclosing functions were delimited by prologue and next-start, and each match was checked by the verifier against the raw words. The table lists only matches the verifier confirmed. Confidence: H = several independent anchors inside one function plus callers checked; M = the call shape or a unique constant is verified but the role is inferred from neighbours.

## 7. Strategy recommendation: functional, with a thin matching-tool veneer

The design spec already rules out a byte-matching decompilation. The groundwork confirms the reasons and adds new ones:

- **Matching** needs the proprietary Metrowerks compiler (`mwcps2-3.0.1b119`, a Windows binary run under wibo or Wine) that we cannot commit, run in CI or even confirm as the exact build; splat with the MWCCPS2 profile; a linker script reproducing one RWX segment with gp `0x004E8670`; and a link that includes the vendor code we will never own (RenderWare, RWA, Sony SDK 2.8, CRT, DirtySock, Logitech: about 3,450 of the functions, by the GPL project's count). Matched code is written in CodeWarrior idioms and would be ported to clang/emscripten afterwards, two codebases. A GPL project already occupies this niche on this exact ELF, so an MIT matching repo would duplicate it while having to prove the independence of every name.
- **Functional** means our C++ compiles into the runtime and runs in the same process, on the same 32 MB guest RAM, replacing one recompiled function at a time by address, A/B-switchable like reB3's backend switch. Verification is the differential harness (`docs/re/function-harness-spec.md`): identical return registers, callee-saved registers, changed memory ranges, I/O stores and syscalls on snapshots from real play, with the EE FPU reproduced bitwise by the fork's `fp::` helpers. The verifier confirmed the key runtime facts: `ps2run` is single-threaded, direct calls bypass `dispatch()`, the save state is complete, and a call harness is the existing `run_guest()` loop with guards. Costs: there is no proof that a function is complete; CodeWarrior layout facts (vtable slot order, static-init order, literal pooling) are inferred rather than compiled; struct layouts stay at retail offsets while recompiled neighbours read the same bytes, so decompiled code reads guest memory through typed accessors until a whole subsystem is ours.
- **Hybrid-lite** adds the matching tools only where they help reading: splat + spimdisasm as a disassembly and organisation layer driven by our symbol database (output outside the repo), m2c `mipsee` for a first-pass reading of integer code, objdiff optional, decomp.me's mwcps2 as an investigative aid for compiler idioms if a window has access, never as a build dependency. Never permuter or frogress: they measure byte matching. The progress metric is bytes of game code (our own owner classification) whose functions are `verified`, reported by our own tool into `docs/PROGRESS.md`.

Two design points follow from how the fork emits code (verified in `recomp/codegen.cpp` and `runtime/include/ps2/fpu.hpp`): (a) an `ee::f32` value type over `fp::add/sub/mul/div/sqrt/rsqrt` plus `guest_ptr<T>` accessors over `ld*/st*` are the first things to write in `src/`, because host `float` rounds to nearest and keeps denormals while the EE model truncates and flushes, so native floats would never match the oracle; (b) the per-function hook is a codegen feature of `eerecomp` (a one-line check at each function label) plus a `dispatch()` check for indirect calls, not a runtime table alone, because direct `jal` calls never pass through `dispatch()` and same-unit register jumps do not either.

Precedents closest to us: Tenkaichi3Decomp (data tables "as shape only", values from the user's disc), ssxog (functional on purpose), reB3 (per-feature backend switch, differential validation).

## 9. Proposed repo layout and symbol-database format

The design spec names `game/` for port config and the hooks list and `src/` for our C++; the tooling reader proposed `decomp/`. Recommendation: keep the spec's names.

```
Burnout3Decomp/
  game/
    symbols/SLUS_210.50.tsv      the symbol database (format below); the only source of names
    symbols/structs/*.tsv        one file per struct: offset, size, type, our field name, evidence
    hooks/burnout3.hooks         addresses whose decompiled version replaces the recompiled one
                                 ("0x0021BFA0 valuedb_hash_key", one per line), exported from the TSV
    splat/burnout3.yaml          platform ps2, compiler MWCCPS2, gp_value 0x004E8670; asm_path,
                                 target_path and symbol_addrs_path point outside the repo (~/b3/out/splat)
  src/
    ee/                          f32.hpp (fp::* wrapper), guest.hpp (guest_ptr, ld/st), abi.hpp (arg/ret shims)
    hooks/                       hooks_table.cpp (the explicit address -> function table) and the
                                 decompiled functions, one directory per subsystem below it:
                                 valuedb/ physics/ ai/ traffic/ score/ frontend/ ...
  tools/                         (other session) elf-anchors.py, symdb.py (validate, export splat/hooks/names,
                                 import anchors), difftest.py (snapshot + call + diff), progress.py, nogamedata.py
  tests/
    unit/                        data-free: ee::f32 against fp::* edge cases, guest accessors, pure functions with
                                 synthetic inputs (base-40 codec, the hash with a recomputed table)
    oracle/                      needs the ELF and snapshots under ~/b3/out/snapshots; skipped unless PS2_ORACLE=1
  docs/re/ docs/research/ docs/PROGRESS.md docs/superpowers/
  external/FORK.md
```

Committed: the TSV symbol DB, structs, hooks list, splat YAML, our C++, tests, docs. Never: the ELF, ISO, generated C++, splat asm output, snapshots, the exported `symbol_addrs.txt`, retail tables (the CRC table, parameter defaults, wave names), any compiler binary.

**Symbol DB format**: tab-separated, one line per symbol, sorted by address, LF endings, header row

`address	name	kind	size	type	owner	evidence	status	note`

- `address`: `0x%08X` virtual address. `name`: our C identifier, never copied from the GPL project (`fn_0021BFA0` until named). `kind`: `func | data | rodata | bss | vtable | jtbl | ctor | label | string`. `size`: hex or `?`. `type`: C prototype or type, empty if unknown. `owner`: `game | rw | rwa | sce | crt | dirtysock | logitech | vu`, assigned from the boundary table of section 2. `evidence`: one or more of `C` (oracle-confirmed behaviour), `S` (string or constant anchor at the address), `X` (call graph or xref), `R` (reB3 crosswalk inference), `G` (guess). `status`: `recomp | draft | verified`. `note`: short, may cite a `docs/re/*.md`.
- Consumers: `symdb.py export-splat` writes `name = 0xADDR; // type:func size:0x..` for splat; `export-names` writes the flat names file for `eerecomp --names` (labels get `// name` comments, probe and halt output get names); `export-hooks` writes the hooks file from rows with `status=verified`. The fork consumes two flat files (addresses + names; addresses to hook) and never depends on our schema. Validation in CI: sorted, unique, valid identifiers, owners and evidence from the allowed sets, no overlapping sizes.
- CI is data-free: validate the TSV; clone the MIT fork at the pinned commit and compile `src/` + `tests/unit` against its `runtime/include` (no ELF needed); run the unit tests; run the no-game-data gate over every tracked file (ELF magic, `$Id: //RenderWare`, 256-word tables, `.iso`/`.bin` sizes). Oracle tests run only on Mark's box.

## 11. Risks

- **FPU parity.** The force pass, integrator, chassis contact and most collision functions are VU0 macro-mode code (`lqc2`/`qmtc2`/vector ops). Decompiling them means reproducing `ps2::vu::*` semantics, not just `fp::*`; the harness compares `c.vu0` only with `--compare-vu`. Start with scalar leaves.
- **Harness blind spots.** Functions that wait on the IOP, switch threads or kick DMA are not harness material and stay recompiled; the driver marks them SKIP. A custom `SetSyscall` handler could loop the harness without the guard the verifier added.
- **Snapshot churn.** Every `kStateVersion` bump (gap 007 did 3 to 4) invalidates the corpus; regenerating is one scripted run, but keep the command next to each corpus.
- **Struct drift.** Until a subsystem is wholly ours, our code must read and write guest RAM at retail offsets; a host struct introduced too early breaks recompiled neighbours silently. The racecar and player-car containers differ from Xbox already.
- **Name independence.** A GPL matching project exists on this ELF with 70 named functions. Our names must come from our own evidence (`S`, `X`, `C`) or from reB3 (MIT, `R`); never from that repo. The leaked RenderWare 3.7 source used by two PS2 projects must never be opened.
- **Vendor code.** About 3,450 functions (RenderWare, RWA, Sony SDK, CRT, DirtySock, Logitech, Speex) stay recompiled indefinitely; the game code is roughly 5,650 functions and 2.7 MB. The progress metric must count only `owner=game`.
- **Recompiler false functions and false splits** (`0x004C7220`, `0x004D1B68`, `0x00484890`, the split at `0x001C1C3C`): harmless now, but the symbol DB should record them so nobody names them.
- **Performance of the 3b entry check**: one load and a predicted branch per function entry in all builds; measure with `PS2_TIME` before and after.
