## Shims

All in `src/hooks/hooks_table.cpp`; the function files are untouched. Pointer arguments are
guest addresses turned into host pointers into EE RAM with `ps2::host_ram()`; pointers stored
inside guest objects (the ring header address in the descriptor) are read with `ld32` and
translated the same way. Points worth recording:

- `ring_index_advance`: a zero delta copies the whole 64-bit `a1` into `v0` and reads no
  memory; otherwise the result is zero-extended. The shim builds a host `RingDesc` whose
  header pointer is the translated guest address.
- `path_extension_after_dot`: no dot returns the whole `a0` register; a hit returns the
  guest address of the extension, sign-extended from 32 bits.
- `find_key64_slot`: the key is all 64 bits of `a1`.
- `lowest_set_bit_index` uses `ee::abi::hook<&fn>` directly; the rest are written out.
- `sap_compare_x` and `select_gear_under_rev_limit` also reproduce the FPU condition bit,
  which the decomp log listed as "not reproduced". That is what lets `--strict` compare
  `fcr31` for them. For the comparator the bit is set exactly when the answer is -1. For the
  gear function it is left alone when the count is 1 or less, and otherwise is set exactly
  when an entry qualified (the result is below the count).
- `select_gear_under_rev_limit` and `build_texture_uv_rect` OR `0x30000` into `fcr31` on a
  divide by zero and never assign.

No shim needed a fix after the first run: every function passed first time.

## Not covered

- **The divide-by-zero flags being set.** Every snapshot of this corpus already has
  `0x30000` in `fcr31` on entry (`0x00030000` in eleven states, `0x00830000` in one), so a
  shim that forgot the OR would pass too. What is tested is that the hooks leave `fcr31`
  otherwise intact, including the condition bit where it was set. Testing the OR itself
  needs a way to clear `fcr31` before the call (a `--fcr31` option on the harness) or a
  snapshot taken before the flags are first raised.
- **64-bit argument registers.** The harness sets argument registers from 32-bit values and
  sign-extends them. `find_key64_slot` was therefore searched only with keys that are
  sign-extended 32-bit values (the tables hold arbitrary 64-bit keys), and the "malformed
  upper half" cases of the other functions cannot be given. Also wanted: a way to pass a
  full 64-bit value.
- **The stale `f3`.** The corpus has two distinct `f3` values across its twelve states, so
  the `count <= 1` path of the gear function was checked with those two only.
- **Out-of-domain inputs** named in the decomp log (hash keys with bytes above 0x7F, empty
  paths, a wrapping ring of capacity 0, counts above 128) were left out on purpose.
- All twelve states are from the menus; none of these functions depends on game state beyond
  its arguments, except the gear function's `gp` constant, which is the same in all twelve.
